# [0.4.0] - 2026-08-01

## Breaking Changes

### Signature of when() functions changed in all event wait functions
**For example**: `vv.async.wait_for_mouse_move(nil, function(event) end)` now accepts the raw mouse_move event,
instead of receiving a wrapped object with redundant information that this was raised by 'mouse_move'

**Migration**: 
1. Access the event directly instead of unwrapping `event.data`.
2. Call `vv.async.wait({ event = 'mouse_move', when = function(registration, event) end})` to continue receiving redundant information.

### Process API no longer emits global events

Previously, the process with id `X` would emit events on `process.stdout.X` with the output as a payload.
The new process API requires a callback to be defined at creation time. If a callback is provided, the stream
will be created. Otherwise no stream will be created:

```lua
local proc = vv.api.process_spawn('cat', {
  on_exit = function(id, exit_code, signal) 
    if exit_code ~= nil then
      print(string.format("Process <%d> exited with exit code %d", id, exit_code))
    else
      print(string.format("Process <%d> exited due to signal", id, signal))
    end
  end,
  -- If true, stdin is available. Otherwise it is never created
  stdin_pipe = true,
  on_stdout = function(id, data, stream)
    if data == nil then
      print(string.format("stdout closed (<%d>)", id))
    else
      print(string.format("stdout from <%d>: %s", id, data))
    end
  end,
  on_stderr = function(id, data, stream)
    if data == nil then
      print(string.format("stderr closed (<%d>)", id))
    else
      print(string.format("stderr from <%d>: %s", id, data))
    end
  end,
})
vv.api.process_write_stdin(proc, 'hello cat')
-- stdin must be explicitly closed to indicate to 'cat' that no more input is coming
vv.api.process_close_stdin(proc)
```

**Migration**
1. Switch to the new callback based API
2. If async is desired, use the high-level process API:

```lua
local process = require('velvet.process')
local cat = process.spawn({'cat'}, { stdout = true, stdin = true })
cat.stdin:write("hello cat\n")
cat.stdin:close()
local line = cat.stdout:line() -- hello cat
local exit_code = cat:wait_for_exit()
```

### Processes now exit on vv reload

This does not affect terminal applications. Their behavior is unchanged.
This only affects the old process API. It was way too easy to leak processes.
No direct migration path is offered, but it is of course possible to manage process lifteimes
in infinite ways outside of velvet.

### vv.api.get_focused_window() now returns nil instead of 0

Code that expects `0` to mean "no window is focused" should check for `nil` instead.

### velvet.diagnostics.logpanel deleted

The new CLI action, `vv log`, is much more useful.

### vv.async wildcard waits removed

Previously it was possible to wait via `vv.async.wait('window.**')` to receive all named events prefixed with `window.`
This is no longer the case. The intention was for the event system to continue composing on top of named strings, but `async.event_source()`
is the preferred way to compose events now. The wildcard implementation saw extremely limited use in the first place.

If you used it, I recommend composing events via event sources instead. The number of built-in string events is limited enough
that they can trivially be enumerated, and no builtin events compose new events on top of them anymore.

Composed event example:

```lua
local composed = vv.async.event_source()
vv.async.run(function()
  for reg, evt in vv.async.stream('window_closed', 'window_created') do
    composed:emit({reg, evt})
  end
end)

local closed_or_created = composed:wait()
```

### velvet.cli_commands moved to velvet.cli

**Migration:** `require('velvet.cli')` instead.

### Almost all events renamed

This only affects you if you are using `async.wait(evt)` with string literals.
`vv.events` is not affected.

**Migration:** Replace '.' with '_' in all string literals passed to `async.wait()`.

## Highlights

### vv.async.event_source()

The async system has received major improvements and bugfixes. The main addition is the concept of an `event source`.
Event sources are used throughout the standard velvet components already, and offter a distinct advantage over string literals:

1. They can be annotated with a type signature so luals knows exactly what is returned via event:wait(). Likewise, when diagnostics are available when emitting via event:emit(data).
2. They are very cheap to create, and incur no cost to the async system until they are awaited.
3. They are normal lua objects, and can thus be garbage collected, automatically clearing them from the async internals.

It is very easy and convenient to compose high-level events from low-level events and propagate them via event sources.
In fact, this is the backbone of the new statusbar and process API.

### Customizable Status Bar

It is now possible to create customizable statusbar elements. The default preset configures the statusbar to be very similar to the
old hardcoded statusbar, but each component is available as a builtin and can now be configured separately.

The existing builtins are a great resource for how to write custom status elements, but the basics are as follows:

1. Register a new named statusbar element via `statusbar.register()`:

```lua
local statusbar = require('velvet.extras.statusbar')
statusbar.register('my_element', {
  default_options = { foreground = '#000000', background = 'red', bold = true },
  content = function(user_data, trigger, trigger_event)
    -- content is called every time a member in `update_triggers` is signaled.
    -- update_triggers accepts the exact same things as `vv.async.wait()`.

    -- the parameters are as follows:
    -- 1. user_data is an element-specific table which the bar can use to store information.
    -- This is useful because it is possible to specify the same bar element twice with different options.
    -- 2. trigger is the event which caused content() to be called. In this case, it will either be
    -- 'on_key' or nil, 1000 miliseconds passed with no key events.
    -- content() will also be called once with nil at startup.
    -- The statusbar will render immediately after this function returns, but it is legal
    -- to use async functions in here. Nothing will be delayed if you run use the process API to invoke a curl command.
    -- 3. trigger_event contains event data for teh trigger. For 'on_key' this would contain information about the key event.

    return "my element"
  end,
  -- content() is polled once a second, or whenever a key is pressed
  update_triggers = { 'on_key', 1000 },
})
```

After registering the element, the definition is saved in the statusbar implementation, but it is inactive
until it is actually added to a statusbar. To add our new element to a statusbar, add it to a section:

```lua
local preset = require('velvet.presets.dwm').setup( { opt } )

-- override the center section
preset.statusbar:set_center({'my_element'})
-- OR append center elements
local center = preset.statusbar:get_center()
center[#center+1] = 'my_element'
preset.statusbar:set_center(center)
```

#### Setup

The statusbar can be configured by passing a `statusbar` key to the `setup()` function of the default preset:

```lua
local preset = require('velvet.presets.dwm').setup({
  statusbar = {
    -- left aligned elements
    left = {
      {
        -- some elements define custom options you can override,
        -- such as active/inactive colors for dwm_tags
        name = 'dwm_tags',
        options = {
          active_background = 'red', -- focused view
          inactive_background = 'blue', -- non-focused views
          foreground = '#000000', -- text color
          show_unoccupied_tags = false,
        }
      },
      {
        -- most elements will respect these four options:
        -- foreground, background, italic, bold
        name = 'pending_keys',
        options = {
          foreground = 'white',
          -- setting background to nil will cause the element to inherit the bar background
          background = nil,
          bold = false,
          italic = false,
        },
      },
      -- if the default options are fine, you can use the name as a shorthand, no table needed
      'copy_mode'
    },
    -- centered elements, empty by default
    center = {  },
    -- right aligned elements
    right = { 'servername', 'clock' },
    -- bar position. can be 'top' or 'bottom'
    position = 'bottom',
    -- background color of unoccupied bar space.
    background = '#181825'
  },
})
-- for further bar manipulation, the bar instance can be accessed via preset.statusbar
local bar = preset.statusbar
bar:set_center({}) -- remove all center elements
```

#### Builtins:

 - **clock** displays the current time in a 'HH:MM' format
 - **copy_mode** displays the current copy_mode state. The element disappears when copy_mode is not active.
 - **dwm_tags** shows the currently occuppied and focused dwm tags.
 - **servername** statically displays the name of the current velvet instance. Same as the `$VELVET` environment variable.
 - **window_title** shows the title of the currently focused window.
 - **pending_keys** shows unresolved keys, meaning an indicator will appear when the prefix key is pressed.


### Async Process API

Built in the new low-level callback-based process API, a new high-level process API is available.
It integrates cleanly with the existing async system, and offers line-buffered stdout / stderr.

The main use-case is for integrating with the statusbar. In many cases, it is convenient to
run some shell script or binary in an interval and display its output, such as a battery indicator.

The async API cleanly maps line-wise process output to immediate statusbar updates.

Example:

```lua
local producer = require('velvet.process').spawn({'bash', '-c', [[
for ((i=1;i<=100;i++)); do
  echo "$i/100"
  sleep 1
done
]]}, { stdout = true })
-- lazy iterator automatically yields until a new line is available
for line in producer.stdout:lines() do
  print(line)
end
```
